## 7. Architect for testability

Minecraft code is difficult to test if every rule is buried inside event handlers and game classes.

### Bad shape

```java
public void onPlayerInteraction(Player player, World world, BlockPos pos) {
    // 150 lines containing:
    // validation
    // random calculations
    // inventory updates
    // persistence
    // particles
    // networking
}
```

### Better shape

```text
Minecraft event adapter
        ↓
Use-case/service
        ↓
Pure domain rules
        ↓
Result
        ↓
Minecraft effects adapter
```

For example:

```java
public record RitualInput(
    int nearbyCandles,
    boolean isNight,
    int playerLevel
) {}

public record RitualResult(
    boolean successful,
    int levelCost,
    RewardType reward
) {}

public final class RitualRules {
    public RitualResult evaluate(RitualInput input) {
        // Pure Java logic
    }
}
```

The event handler translates Minecraft state into `RitualInput`, calls the pure logic, and applies the result.

This lets the agent write and run fast JUnit tests without launching Minecraft:

```java
@Test
void ritualFailsDuringDay() {
    RitualInput input = new RitualInput(8, false, 30);

    RitualResult result = rules.evaluate(input);

    assertFalse(result.successful());
}
```

AI-generated code becomes dramatically safer when most behavioural rules can be checked this way.


Add whichever formatting and static-analysis tasks you configure:

### Also maintain two smoke-test profiles

#### Client smoke test

- Game starts.
- A world can be loaded.
- Registries complete without errors.
- New assets and translations resolve.
- Primary feature works once.

#### Dedicated-server smoke test

- Server starts without client-class errors.
- A player can connect.
- Feature works with server authority.
- Save/reload does not lose data.
- Malformed or invalid packets do not crash the server.

A mod that works in an integrated single-player server can still crash a dedicated server.

## 10. The most dangerous AI failure modes

### Hallucinated APIs

Minecraft modding APIs vary heavily by:

- Minecraft version
- Loader
- Loader version
- Mapping set
- Fabric API or NeoForge version

A method may be real but belong to another version.

**Mitigation:**

- Pin versions.
- Give the agent the generated project.
- Tell it to inspect dependency sources.
- Use official documentation and the template reference project.
- Compile after every meaningful change.
- Never accept “this should compile.”

### Fabric/NeoForge contamination

The model may import examples from the wrong loader.

**Mitigation:**

```markdown
This is a Fabric project. Never use Forge or NeoForge classes,
annotations, event buses, registration patterns, or documentation.
```

Put that in `AGENTS.md`.

### Client/server boundary errors

Typical problems:

- Importing renderer classes in common initialization
- Trusting the client to award items
- Mutating server state only on the client
- Sending excessive packets
- Accessing a world before it exists

**Mitigation:** require every feature plan to include a short section titled **Sides and authority**.

### Giant rewrites

Agents sometimes replace working infrastructure instead of adapting it.

**Mitigation:**

- Limit task scope.
- Require a plan before edits.
- Review `git diff --stat`.
- Reject unrelated changes.
- Commit after every accepted slice.

### Mixins used too early

Mixins are powerful but highly sensitive to game internals.

**Mitigation:** prefer:

1. Loader API
2. Events/hooks
3. Access wideners when appropriate
4. A narrowly targeted mixin as a last resort

Require a written justification for each mixin.

### Assets forgotten

Java can compile while the feature is broken because of:

- Missing translation keys
- Wrong resource paths
- Missing models or textures
- Invalid JSON
- Incorrect identifiers

Include resources in every feature’s acceptance criteria.

```text
│   ├── ModItems.java
│   ├── ModBlocks.java
│   ├── ModEntities.java
│   └── ModComponents.java
├── domain/
│   ├── spell/
│   ├── progression/
│   └── ritual/
├── service/
│   ├── SpellService.java
│   └── ProgressionService.java
├── persistence/
│   ├── PlayerProgressData.java
│   └── WorldStateData.java
├── network/
│   ├── ModNetworking.java
│   └── payload/
├── command/
├── integration/
└── client/
    ├── MyModClient.java
    ├── render/
    ├── screen/
    └── model/
```

Do not force this structure onto a tiny mod, but preserve these boundaries:

- **Registration:** declares game objects.
- **Domain:** contains rules.
- **Services:** coordinate use cases.
- **Persistence:** stores state.
- **Network:** crosses client/server boundaries.
- **Client:** contains rendering, UI, keybindings, and client-only effects.
- **Integration:** isolates optional mod compatibility.

I'd be glad to help you architect this. Before I dive into recommendations, one important flag: I don't have reliable knowledge of "Mistral Medium 3.5" or the current state of Devstral Small — my training data has a cutoff, and given today's date (August 2026), there's likely been a lot of model iteration I'm not aware of. That said, the architectural principles for "shipping a Minecraft mod with a mid-tier coding model" are pretty stable, so let's get into it.

## The core problem you're solving

Mid-tier coding models are generally good at *local* code generation and bad at *global* reasoning about unfamiliar, deeply-nested APIs. Minecraft modding is almost pathologically hostile to the second category:

- Massive, poorly-documented API surface (Forge/Fabric/NeoForge)
- Version churn — code for 1.20 often doesn't work on 1.21
- Obfuscation/mappings layers (Mojmap vs. Yarn vs. SRG)
- Registry/lifecycle timing rules that fail silently or crash cryptically
- Client/server split where getting it wrong causes desync, not a compile error

A weaker model will confidently generate 1.16-era Forge code because that's what dominated its training data. This is the single biggest failure mode you'll hit.

## Recommendations

### 1. Pin your stack and put it in every prompt

Decide up front: **Minecraft version, loader (Fabric/NeoForge/Forge), mappings, Java version, Gradle/loom version.** Write these into a `CONTEXT.md` or `.cursorrules`-style file that gets injected into every coding session. Something like:

```
Target: Minecraft 1.21.x, NeoForge, Mojang mappings, Java 21
DO NOT use: @Mod.EventBusSubscriber annotations from Forge 1.16-1.18 style,
ForgeRegistries direct registration, or any RegistryObject patterns.
DO use: DeferredRegister with the modern lifecycle, IEventBus passed to @Mod ctor.
```

The "DO NOT" list is doing more work here than the "DO" list. You'll build it up as you catch the model reaching for stale patterns.

### 2. Give the model ground truth, not memory

This is the highest-leverage thing you can do. Rather than hoping the model remembers the API:

- **Clone a reference mod** in your target version/loader and keep it in the workspace. Point the model at it: "match the registration pattern used in `reference/src/main/java/.../ModItems.java`."
- **Have the decompiled/sourced Minecraft jar available** so the model can read actual method signatures rather than hallucinating them.
- Fabric/NeoForge both publish official example mods — start from those templates rather than from scratch.

A mid-tier model reading correct code and adapting it will outperform a frontier model recalling from memory.

### 3. Make the feedback loop tight and automated

The model needs to *find out it was wrong* quickly and cheaply.

- Get `./gradlew build` running fast. Compile errors are your best friend — they're precise, and models are good at fixing them.
- Set up `runClient` / `runServer` with a datapack/world that puts you in a test scenario in <20 seconds.
- Consider **GameTest** (Fabric and NeoForge both support Mojang's GameTest framework). Automated in-game tests that a model can run and iterate against are enormously valuable — they convert "does this work?" from a manual 2-minute check into a scriptable assertion.

If you only do one thing from this list, do GameTest for your core mechanics.

### 4. Architect for small, isolated units of work

Structure the mod so that features are additive and independent:

```
mymod/
  registry/       # all DeferredRegister declarations, one file per type
  content/
    blocks/       # one file per block, self-contained
    items/
    entities/
  network/        # packet definitions, isolated
  client/         # renderers, screens — strictly client-only
  data/           # datagen providers
```

The goal: any single task should be "create/modify one file, plus add one line to a registry file." That's a task shape mid-tier models handle well. Tasks that require touching six files with subtle ordering constraints are where they fall apart.

Do the registry scaffolding and the client/server boundary design **yourself, once, carefully**. Then the model is filling in slots rather than making architectural decisions.

### 5. Use datagen aggressively

Minecraft mods need enormous amounts of JSON: recipes, loot tables, models, blockstates, tags, advancements. Hand-writing these is error-prone and models fumble the schemas.

Instead, use the data generation system so JSON is produced from Java code the model can typecheck. `./gradlew runData` catching a mistake at compile time beats a silent missing-texture bug.

### 6. Establish a "known-good" ratchet

Commit early, commit often, and keep the build green. When the model produces something that compiles and works, commit immediately. Mid-tier models are prone to "fixing" things by breaking adjacent code — you want cheap rollback.

Consider a pre-commit hook that runs `./gradlew build` and rejects broken commits.

## Where to keep humans (you) in the loop

Be deliberate about the division of labor. Reserve for yourself:

- **Initial project setup and build config.** Gradle + loom/neogradle is finicky and failure here is opaque. Use an official template.
- **Client/server split decisions.** Getting this wrong produces bugs that only show up in multiplayer, hours later.
- **Registry lifecycle and event bus wiring.** Silent failures live here.
- **Networking packet design.** Serialization bugs are nasty to debug.
- **Performance-sensitive code** (anything in a tick loop or chunk-gen path).

Delegate freely:

- Individual block/item classes following an established pattern
- Recipe/loot table datagen providers
- GUI screens (given a reference)
- Config definitions
- Refactors with clear mechanical rules
- Test writing

## Suggested build order

1. **Week 0:** You set up the project from an official template. Verify `runClient` works. Commit. Write `CONTEXT.md`.
2. **Week 0.5:** You add one block and one item manually, wiring the full registry path. This is your reference pattern.
3. **Then:** Hand the model "add block X following the pattern in ModBlocks/ExampleBlock." Verify it works. This validates your whole loop before you've invested much.
4. **Scale up:** Content first (blocks, items, recipes — high volume, low risk), then mechanics, then anything touching networking or rendering.

Deliberately front-load a *boring* feature to test the pipeline. Resist starting with the exciting centerpiece mechanic.

## Prompting notes for weaker models

- **One task per message.** Don't batch.
- **Paste the actual error text**, not a summary.
- **Ask for the file, not a diff.** Mid-tier models often generate malformed diffs.
- **When it fails twice on the same thing, stop and give it more context** rather than re-prompting. Two failures usually means missing information, not insufficient effort.
